# 2. Требования

Требования восстановлены по заданию курсовой и коду прототипа. Столбец «Проверка» — результат [сценариев](../scenarios/result.txt) на запущенной системе: ✅ выполняется, ❌ расхождение (подробно — в [разборе](06-gap-analysis.md)), ⏳ не проверялось.

## Пользовательские истории

| ID | История |
|---|---|
| US-1 | Как клиент, я хочу подать заявку онлайн и сразу получить номер, чтобы не ждать звонка |
| US-2 | Как клиент, я хочу по номеру видеть статус заявки, чтобы понимать, что происходит |
| US-3 | Как банк, я хочу автоматически решать типовые заявки, чтобы специалисты занимались только сложными |
| US-4 | Как кредитный специалист, я хочу видеть пограничные заявки с данными и признаками и принимать по ним решение |
| US-5 | Как владелец процесса, я хочу, чтобы заявка не терялась ни при сбоях, ни под нагрузкой |

## Функциональные требования

| ID | Требование | История | Проверка |
|---|---|---|---|
| FR-1 | Сервис принимает заявку: возраст 18–75, доход > 0, платежи ≥ 0, сумма > 0, срок 1–84 мес., тип занятости из справочника. Нарушение → 422 с перечнем полей | US-1 | ✅ сц. 3 |
| FR-2 | Принятая заявка получает статус `PROCESSING`, ответ 202 с номером | US-1 | ✅ сц. 1 |
| FR-3 | Признаки считаются по формулам из [правил решения](05-decision-rules.md) и передаются в очередь сообщением по [контракту](api/asyncapi.yaml) | US-3 | ✅ сц. 1 |
| FR-4 | Решение выносится по таблице решений: одобрение, ручная проверка или отказ | US-3 | ❌ сц. 5 |
| FR-5 | Решение учитывает запрошенную сумму и срок: платёж по новому кредиту входит в долговую нагрузку | US-3 | ❌ сц. 4 |
| FR-6 | Заявки со статусом `MANUAL_REVIEW` видны специалисту с исходными данными, признаками и score | US-4 | ✅ сц. 2 |
| FR-7 | Специалист принимает решение только по заявке на ручной проверке; иначе 409, неизвестная заявка — 404 | US-4 | ✅ сц. 2а |
| FR-8 | Повторная отправка заявки с тем же номером не создаёт повторной обработки и возвращает текущий статус | US-5 | ❌ сц. 6 |
| FR-9 | Сообщение, которое нельзя обработать, сохраняется в очереди ошибок с причиной, заявка получает статус `FAILED` | US-5 | ❌ сц. 9 |
| FR-10 | Статус неизвестной заявки — 404 | US-2 | ❌ возвращается 200 с `NOT_FOUND` |
| FR-11 | Решение специалиста фиксируется с кодом причины из справочника, автором и временем | US-4 | ❌ нет кода причины и автора |

### Критерии приёмки ключевых требований

**FR-5.** Сумма кредита влияет на решение.

```gherkin
Дано   клиент: доход 85 000 ₽, текущие платежи 12 000 ₽, сотрудник, 25 лет
Когда  он запрашивает 5 000 000 ₽ на 12 месяцев
Тогда  PTI с учётом нового платежа больше 0,60
И      заявка получает статус REJECTED с причиной PTI_TOO_HIGH
```

**FR-8.** Идемпотентность приёма.

```gherkin
Дано   заявка REQ-001 уже получила статус APPROVED
Когда  клиент повторно отправляет REQ-001 с теми же данными
Тогда  ответ 200 со статусом APPROVED
И      новое сообщение в очередь не публикуется
Когда  клиент отправляет REQ-001 с другими данными
Тогда  ответ 409 «номер заявки уже использован»
```

**FR-9.** Ошибочное сообщение не теряется.

```gherkin
Дано   в очередь пришло сообщение без обязательного поля features.debt_ratio
Когда  система принятия решений не может его обработать
Тогда  сообщение попадает в processed_data_dlq с заголовком причины
И      заявка получает статус FAILED
И      дежурный получает оповещение
```

## Нефункциональные требования

| ID | Требование | Проверка |
|---|---|---|
| NFR-1 | Надёжность: заявка не теряется при недоступности системы принятия решений — сообщение ждёт в очереди | ✅ сц. 8 |
| NFR-2 | Целостность: 40 одновременных заявок → 40 ответов 202 и 40 решений, без ошибок 500 | ❌ сц. 7 |
| NFR-3 | Ответ на подачу заявки ≤ 1 с (p95), в том числе при недоступном брокере: заявка принимается и публикуется позже | ❌ сц. 10: 20 с и 503 |
| NFR-4 | Решение по типовой заявке ≤ 5 с от подачи (p95) | ⏳ |
| NFR-5 | Безопасность: интерфейс специалиста и API решений — только для аутентифицированных сотрудников с ролью «кредитный специалист» | ❌ нет аутентификации |
| NFR-6 | Персональные данные (возраст, доход, долги) хранятся и передаются в соответствии со 152-ФЗ: шифрование при хранении, журнал доступа | ❌ открытый JSON-файл |
| NFR-7 | Трассировка: каждое событие в логах содержит `request_id` | ⚠️ частично: в логе ошибки обработки сообщения номера заявки нет |
