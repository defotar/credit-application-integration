# 6. Разбор расхождений

Прототип запускался через `docker compose up`, затем [11 сценариев](../scenarios/run.py) проверили требования на живой системе. 5 сценариев прошли, 6 выявили расхождения. Полный вывод — [scenarios/result.txt](../scenarios/result.txt).

| ID | Расхождение | Сценарий | Риск | Приоритет |
|---|---|---|---|---|
| G-1 | Сумма и срок кредита не влияют на решение | 4 | кредит в 5 годовых доходов одобряется автоматически | критический |
| G-2 | Оба сервиса и интерфейс специалиста пишут в один JSON-файл | 7 | потеря заявок и ошибки 500 под нагрузкой | критический |
| G-3 | Правила решения в коде расходятся с документацией | 5 | заявки, которые по правилам должны получать отказ, уходят специалистам | высокий |

## G-1. Сумма кредита не участвует в решении

**Факт.** Тот же клиент с запросом 150 тыс. и 5 млн ₽ на 12 месяцев получает одинаковый score 76,43 и `APPROVED`. Платёж по второму кредиту — около 463 тыс. ₽ в месяц при доходе 85 тыс.

**Причина.** `calculate_features` не использует `requested_amount` и `requested_term_months`; `debt_ratio` считает только текущие платежи.

**Требование.** FR-5: PTI с платежом по новому кредиту и отсечение при PTI > 0,60 — см. [таблицу решений TO-BE](05-decision-rules.md#таблица-решений-to-be).

## G-2. Общий файл вместо базы данных

**Факт.** Из 40 одновременных заявок 21 получила ответ 500, а из 19 принятых 8 остались без решения (один прогон, числа меняются от запуска к запуску).

**Причина.** Каждый сервис читает весь файл, меняет свою запись и перезаписывает файл целиком через временный файл с одинаковым именем `results.tmp`:
- два процесса одновременно переименовывают один `results.tmp` → `FileNotFoundError` → 500;
- система решений записывает решение поверх версии файла, прочитанной до появления новых заявок → чужие записи пропадают (lost update).

**Требование.** NFR-2. Решение TO-BE:
1. У статуса заявки один владелец — сервис заявок с PostgreSQL, одна строка на заявку.
2. Система решений не пишет в хранилище, а публикует событие `decision.made` в ответную очередь.
3. Переход статуса — условное обновление `UPDATE … SET status = :new WHERE id = :id AND status = :expected`: повторное или запоздавшее событие не перезапишет финальный статус.

## G-3. Пересекающиеся правила

**Факт.** score 36,33 и долговая нагрузка 0,50 → `MANUAL_REVIEW`, хотя в README сказано «score < 40 → REJECTED».

**Причина.** Условия «40 ≤ score < 70 **или** 0,45 < debt_ratio ≤ 0,60» и «score < 40» пересекаются, а порядок проверки нигде не зафиксирован.

**Требование.** FR-4: таблица решений с политикой FIRST и кодами причин — правила не пересекаются по смыслу, порядок явный, каждая строка покрыта тестом.

## G-4. Неидемпотентный приём

**Факт.** Повторный POST по заявке со статусом `APPROVED` возвращает 202 `PROCESSING` и снова публикует сообщение. Решение не портится: система решений пропускает дубликат. Но клиент видит неверный статус.

**Требование.** FR-8: повтор с теми же данными → 200 с текущим статусом, без публикации; с другими данными → 409.

## G-5. Недоступный брокер

**Факт.** Ответ 503 через 20 секунд, заявка остаётся в `PROCESSING` навсегда: сообщения нет ни в очереди, ни где-либо ещё.

**Причина.** Публикация идёт внутри HTTP-запроса с 10 повторами по 2 секунды, а запись о заявке сделана до неё и не откатывается.

**Требование.** NFR-3. Решение TO-BE — шаблон outbox: заявка и сообщение сохраняются в одной транзакции, клиент сразу получает 202, публикацию выполняет отдельный процесс. Схема — в [интеграции](04-integration.md#to-be-outbox).

## G-6. Нет очереди ошибок

**Факт.** Сообщение без признаков опубликовано в очередь, через 3 секунды его нет: `nack(requeue=False)` без dead-letter exchange удаляет сообщение.

**Требование.** FR-9: у очереди `x-dead-letter-exchange` → `processed_data_dlq`; причина ошибки — в заголовке; заявка получает `FAILED`; оповещение при появлении сообщений в DLQ.

## G-7, G-8. Ручная проверка

Интерфейс специалиста открыт без входа, а `POST /manual-review/{id}/decision` принимает решение от любого клиента в сети. Комментарий — свободный текст, автор не записывается.

**Требования.** NFR-5, FR-11:
- вход через корпоративную учётную запись (SSO), роль «кредитный специалист»;
- код причины решения из справочника (`INCOME_CONFIRMED`, `HIGH_DEBT_LOAD`, …) обязателен, комментарий — до 500 символов;
- журнал: кто, когда, какое решение и по какой версии данных заявки.

## Что не проверялось

- Время решения под нагрузкой (NFR-4): прототип хранит данные в файле, замер на нём не покажет поведение TO-BE.
- Устойчивость к перезапуску брокера с сообщениями в очереди: очередь и сообщения объявлены устойчивыми, но сценарий не запускался.
